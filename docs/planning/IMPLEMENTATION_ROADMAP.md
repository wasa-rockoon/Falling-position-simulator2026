# Phase 1〜6 実装ロードマップ

この計画はPhase 0の判断とデータ契約を実装へ落とすための作業順です。Phase 0資料自体はコミット対象にしません。

## 全体方針

- `dev/kotaki` の基準点 `62de923` から進める。
- 自動保存、海上率下限、実行前のHTTP試行数・概算時間表示、「現在の1件完了後」の中断を維持する。
- 既存保存データを破壊せず、移行アダプターを先に作る。
- 画面の大改修前にRunRecord、履歴、海陸判定の契約を実装する。
- `pred-new.js` へ新しい責務を追加しない。特性テストを作ってから段階的に抽出する。
- 各Phaseでbuild、構文検査、単体テスト、影響範囲のブラウザ確認を行う。
- 生成CSV、`node_modules/`、Acorn、Office文書、Phase 0資料をコミットしない。

## Phase 1: 実行・履歴基盤

目的は、分散したグローバル状態、保存処理、履歴を共通Runモデルへ統合することです。

### 実装

1. `js/domain/run-record.js`
   - RunRecord v1、状態遷移、入力正規化、表示用summaryを純粋関数で実装する。
2. `js/core/run-repository.js`
   - IndexedDBへRun本体とHistoryEntryを保存する。
   - 直近50件、pin、実行中保護の保持方針を実装する。
3. `js/core/settings-repository.js`
   - 通常フォーム、プリセット、テーマ、旧Cookie地点の読み書きを一つの入口へまとめる。
4. `js/pred/request-context.js`
   - API URL、予算、待ち行列、中断、診断をRun開始時に固定する。
5. 既存アダプター
   - 愛媛履歴、`pred-job-store.js`、既存localStorage/Cookieを読める移行層を作る。
   - 旧データは削除せず、二重保存期間を設ける。
6. 共通エラー
   - code、利用者向け文、技術情報、retryable、phase、runIdを持つ。
7. 自動保存
   - single、Variant、候補、サンプルの安定境界でRunRecordを保存する。

### 完了条件

- 通常、愛媛、自動探索、不確実性解析がRunRecordを生成する。
- 中断・再読込・再開が共通Repository経由で動く。
- 完了Run、paused Run、failed Runが履歴で区別される。
- 旧プリセット、Cookie地点、既存ジョブを失わない。
- `Illegal invocation` と `requestContext is not defined` の回帰テストを維持する。
- UIコードから新しいlocalStorage/IndexedDB直接操作を追加しない。

## Phase 2: 決定論的な海陸判定

目的は、同じ地点をどの機能から判定しても同じ根拠付き結果を返すことです。

### 実装

1. データ源監査
   - 現行GeoJSONの出典、ライセンス、範囲、解像度、穴・内水面を確認する。
   - 四国周辺の運用精度を満たさない場合は、帰属表示可能なより詳細な海岸線・内水面データへ更新する。
2. `js/geo/land-sea-classifier.js`
   - Polygonの外周と穴、MultiPolygonを扱う。
   - 乱数サンプリングを削除し、決定論的に分類する。
   - geodesicまたは局所投影で海岸距離を計算する。
3. LandSeaResult
   - land、sea、inland_water、unknown、source、confidence、distance、dataVersionを返す。
4. 共通利用
   - 通常、愛媛、自動探索、不確実性解析、放球ウィンドウを同じClassifierへ接続する。
5. 外部API
   - BigDataCloud/Overpassを大量処理の既定経路から外す。
   - 任意の詳細確認でのみ使い、失敗時はunknownのままにする。
6. 検証セット
   - 四国・九州・中国地方、離島、港湾、湖、河川、海岸直近の固定点を追加する。

### 完了条件

- 同じ緯度経度はRun種別に関係なく同じ結果になる。
- 同じデータ版では再読込後も同じ結果になる。
- 内水面を海上率へ含めない。
- unknown率を別表示し、unknownを自動的な合格へ変換しない。
- 自動探索の大量実行でBigDataCloud/Overpassを呼ばない。
- 固定検証点と境界ケースのテストがすべて成功する。

## Phase 3: RESULTS・診断・グラフのUI統一

目的は、結果の読み方と操作の優先度を統一し、画面外へのはみ出しをなくすことです。

### 実装

1. RESULTSを「概要」「比較・グラフ」「履歴」に再編する。
2. 診断ドロワーをアプリ上部の常設入口へ移し、SETTINGSを閉じても開けるようにする。
3. 打ち上げ設定の非表示ボタンを削除する。
4. シナリオ情報を概要内の展開領域へ統合し、空の外部表示ボタンを削除する。
5. 主ボタン、機能ボタン、出力ボタン、危険操作の共通クラスと状態を作る。
6. `CSV再出力` を `CSV出力` に統一する。自動保存はそのまま維持する。
7. 自動探索の候補一覧と履歴を最大高付きリストにし、モーダル内でスクロールさせる。
8. 高度・風速グラフへ説明付き空状態を追加する。
9. 通常Run、愛媛Variant、履歴Runから最大5系列を重ねて比較できるようにする。
10. 地図、表、グラフの系列色と表示ON/OFFを同期する。
11. 画面幅、キーボードフォーカス、色コントラスト、実行中・無効状態を確認する。

### 完了条件

- SETTINGSを表示していなくても診断を開ける。
- RESULTSの主要情報へ2操作以内で到達できる。
- 未予測時に白紙グラフを表示しない。
- 愛媛Variantを複数選択して高度・風速を比較できる。
- 1366×768とモバイル幅で主要モーダルが画面外へはみ出さない。
- ボタン文言、見た目、無効・実行中状態が共通化される。
- 自動保存と手動CSV出力の両方が動く。

## Phase 4: 機能統合と`pred-new.js`分割

目的は、重複した実行・描画・出力処理を共通サービスへ移し、変更影響を限定することです。

### 実装

1. `PredictionRunner`
   - 1条件予測と正規化を共通化し、通常・愛媛・探索・不確実性解析から利用する。
2. `VariantProfileRegistry`
   - BASE + 12条件をデータ定義へ移し、愛媛固有のループ処理を薄くする。
3. `MapLayerRegistry`
   - Run/Variant/不確実性/実測ログ/漁港レイヤーの生成、表示、破棄を管理する。
4. `ChartController`
   - TrajectorySeriesから高度・風速グラフを描く。
5. `ExportService`
   - CSV/KMLをRunRecordから生成し、機能ごとの重複をなくす。
6. `HistoryController`
   - RunRepositoryを使い、再表示、再実行、再開、pin、削除を提供する。
7. 機能統合
   - 全地点一括計算を自動探索プリセットへ移す。
   - 放球ウィンドウを自動探索の気象比較へ移す。
   - 旧破裂計算をガス計算へ統合する。
8. `pred-new.js` からAPI、保存、履歴、出力、チャート、海陸判定を抽出する。
9. 特性テストで通常予測・愛媛出力を固定してから旧関数と死んだ分岐を削除する。

### 完了条件

- 予測HTTP呼出はPredictionRunner/ApiClient以外から直接行わない。
- Variant定義が一箇所にある。
- CSV/KML生成がExportServiceへ一本化される。
- 履歴保存がRunRepositoryへ一本化される。
- `pred-new.js` は通常/愛媛互換接続と最低限の描画調整だけになり、目標1500行以下とする。
- 旧コード削除前後で通常予測と愛媛13条件の結果が一致する。
- 初期化とイベント登録が各機能1回だけである。

## Phase 5: 多地点・大量サンプルの負荷制御

目的は、API呼出が多い探索・不確実性解析を落とさず、途中結果を失わずに完了できるようにすることです。

### 実装

1. すべてのHTTP試行を共通キュー、共通予算、指数バックオフ、Retry-After対応へ集約する。
2. 地点間で公平なラウンドロビン実行にし、1地点がキューを占有しないようにする。
3. 完全一致リクエストをメモリ + IndexedDBで共有し、同時リクエストを統合する。
4. 自動探索は気象粗探索、BASE予測、13条件精査の段階実行を維持する。
5. 全件精査は粗探索不合格も最終評価へ進める。
6. 不確実性解析は最小サンプルから始め、信頼区間の安定を複数バッチ確認して逐次停止する。
7. API上限、最悪試行数、予想時間、キャッシュ見込みを開始前に表示する。
8. 上限到達、通信断、タブ再読込時はpartial/pausedとして保存する。
9. KDEや等高線などCPU処理は必要に応じてWeb Workerへ移し、UIを停止させない。
10. 数千回規模ではローカルTawhiri利用を推奨し、公開API向けの安全な既定上限を設定する。

### 完了条件

- 設定したHTTP試行上限を再試行込みで超えない。
- 中断要求後に次の処理単位を開始しない。
- 再読込後に完了済み候補・サンプルを再送信せず再開できる。
- 429、5xx、timeout、offlineでUIが固まらず、partial/paused結果を保持する。
- 同一リクエストの重複HTTP送信がない。
- 1000サンプル相当のモック負荷試験でメモリが無制限増加しない。
- 全件精査で粗探索不合格を除外しない。

## Phase 6: 品質・公開準備

目的は、他の開発者が変更を検証でき、利用者が主要フローを安心して試せる状態にすることです。

### 実装

1. GitHub Actionsへbuild、構文検査、Nodeテストを追加する。
2. Playwright等で主要ブラウザE2Eを追加する。
   - 通常予測
   - 愛媛13条件
   - 自動探索の開始・中断・再開
   - ガス計算から設定反映
   - 不確実性解析の地図表示
   - 履歴の再表示と出力
3. APIをfixture化し、公開APIへ負荷をかけずにE2Eを再現する。
4. アクセシビリティ、キーボード操作、モバイル、1366×768を確認する。
5. Service Worker更新、オフライン起動、キャッシュ上限、保存データmigrationを確認する。
6. 依存台帳、ライセンス、README、アーキテクチャ、運用手順を最終更新する。
7. エラーメッセージと診断情報から秘密情報・過大な応答本文を除く。
8. 最終的な手動受入チェックリストを実行する。

### 完了条件

- CIでbuild、構文検査、単体テスト、主要E2Eが成功する。
- 通常、愛媛、自動探索、ガス、不確実性、履歴の主要フローがfixtureで再現できる。
- 主要画面に重複ID、未処理例外、ローカル資産404がない。
- PWA更新で無限再読込せず、オフライン時の制約が明示される。
- READMEと実装の保存先・外部通信・機能一覧が一致する。
- 利用者による手動確認へ渡せるリリース候補コミットを`dev/kotaki`へpushする。

## 実装中のコミット方針

Phase 0資料はコミットしません。実装は差し戻し可能な次の単位でコミットします。

1. Phase 1: RunRecord・Repository・移行
2. Phase 2: 海陸判定データ・Classifier・回帰点
3. Phase 3: RESULTS・診断・グラフUI
4. Phase 4: Runner・Map・Chart・Export抽出と旧経路整理
5. Phase 5: 負荷制御・再開・ストレステスト
6. Phase 6: CI・E2E・公開文書

各コミットでPhase外の生成物、CSV、Office文書、`node_modules/` をステージしません。

## Goal全体の完了条件

- Phase 1〜6の各完了条件を満たす。
- 自動保存、海上率下限、全件精査、中断境界を維持する。
- BigDataCloud/Overpassへ依存しない決定論的な大量海陸判定が動く。
- RESULTS、履歴、診断、グラフのUIが統一される。
- 重複機能が共通実行・保存・描画・出力基盤へ統合される。
- 大量実行が予算内で中断・再開でき、途中結果を失わない。
- 自動検証と主要E2Eが成功し、`dev/kotaki`へpushされる。
- 最終確認は利用者がローカルで実運用条件を入力して行える。
